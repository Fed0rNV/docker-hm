# Docker: приложение со счётчиком

Исходное приложение взято из задания без изменений. Основная конфигурация
`compose.yaml` содержит сервисы `app` и `redis` и рассчитана на требования
уровней 8–10. Для демонстрации уровня 6 есть `compose.sqlite.yaml`.
Текст задания сохранён в `ASSIGNMENT.md`.

## Быстрый запуск

Нужны Docker с плагином Compose v2 (с поддержкой `up --wait`) и `curl`.
На macOS можно установить Docker Desktop и дождаться запуска его движка.

Из папки проекта:

```sh
cp .env.example .env
docker compose up -d --build --wait --wait-timeout 120
curl -fsS http://127.0.0.1:8080/
curl -fsS -X POST http://127.0.0.1:8080/increment
docker compose logs
```

При новом хранилище GET возвращает `count: 0`, первый POST — `count: 1`.
В браузере можно открыть http://127.0.0.1:8080/ для чтения счётчика.

Настройки в `.env`:

| Переменная | Назначение | Пример |
| --- | --- | --- |
| `GREETING` | Приветствие в JSON | `"Hello from Fedor!"` |
| `HOST_PORT` | Порт на компьютере | `8080` |

После изменения настроек повторить `docker compose up -d`.
Внутри контейнера приложение слушает порт 8000. Redis доступен приложению
по имени сервиса `redis` на порту 6379. На компьютер опубликован только порт
приложения, с привязкой к `127.0.0.1`.

## Проверки и логи для сдачи

```sh
./scripts/run-all.sh
```

Скрипт последовательно выполняет:

1. `check-basics.sh`: сборка Dockerfile, одиночный контейнер, переменная
   приветствия, увеличение счётчика и логи; затем SQLite с Compose и сохранение
   значения после `down` и повторного `up`.
2. Первый запуск `check.sh` на Redis.
3. Второй запуск `check.sh` на Redis.

Каждый запуск использует уникальные имена проектов и свободный порт,
который назначает Docker. Настройки из пользовательского `.env` не влияют на
проверки. Тестовые volumes удаляются через `trap`; обычный проект не затрагивается.

`check.sh` можно запустить отдельно:

```sh
./scripts/check.sh
```

Он проверяет начальный ноль, пять POST-запросов, пересоздание приложения,
`down/up` без удаления данных, сбой и возврат Redis, ограничения процесса.
После остановки приложения и Redis создаёт tar-копию всего `/data` с правами
и владельцами, удаляет исходные тестовые volumes и восстанавливает копию в
другой проект. После восстановления проверяет значение и следующий POST.
HTTP-запросы, готовность и штатная остановка имеют тайм-ауты.
Ошибка печатает этап, возвращает ненулевой код и запускает очистку.

Логи полного прогона:

- `reports/basics.log` — уровни 4 и 6;
- `reports/check-1.log` — первый полный запуск;
- `reports/check-2.log` — второй полный запуск.

Архивы `reports/backup-*.tar` остаются на компьютере и исключены из Git.
Вывод PASS в логах должен быть получен настоящим запуском.
Текущий статус проверки указан в `REPORT.md`.

## Как устроено решение

`Dockerfile` устанавливает зависимости из `app/requirements.txt`, копирует
приложение и запускает Python с UID/GID 10001. Каталог `/data` принадлежит
этому пользователю, поэтому SQLite может работать в одиночном контейнере
и в именованном volume.

В основной конфигурации `app` использует Redis, его корневая файловая система
доступна только для чтения, память ограничена 256 MiB, CPU — одним ядром.
Python не создаёт `.pyc`. Приложению не нужны локальные файлы данных в режиме Redis.
Оба сервиса имеют healthcheck. Первый запуск `app` ждёт готовности Redis.

Redis хранит данные в именованном volume `redis-data`, использует AOF с
`appendfsync always`. Имя volume получает префикс Compose-проекта; фиксированных
`container_name` и общих volumes между проектами нет.

## Ручные проверки уровня 8

Ниже предполагаются `.env.example` и порт 8080. Если порт изменён,
подставить своё значение.

```sh
curl -fsS -X POST http://127.0.0.1:8080/increment
curl -fsS http://127.0.0.1:8080/
# Записать текущее N.
docker compose down
docker compose up -d --wait --wait-timeout 120
curl -fsS http://127.0.0.1:8080/
# Снова N.

docker compose stop redis
curl -sS -w '\nHTTP %{http_code}\n' http://127.0.0.1:8080/healthz
# 200
curl -sS -w '\nHTTP %{http_code}\n' http://127.0.0.1:8080/readyz
# 503
curl -sS -X POST -w '\nHTTP %{http_code}\n' http://127.0.0.1:8080/increment
# 503

docker compose start redis
# Дождаться 200 у /readyz, затем:
curl -fsS http://127.0.0.1:8080/
# N
curl -fsS -X POST http://127.0.0.1:8080/increment
# N + 1, без перезапуска app.
```

`docker compose down` сохраняет данные. Команда `down -v` удаляет volumes;
в обычном проекте её не надо использовать для проверки сохранения счётчика.

## Отдельный запуск уровня 6

```sh
docker compose -p hw6 -f compose.sqlite.yaml up -d --build --wait
curl -fsS -X POST http://127.0.0.1:8080/increment
docker compose -p hw6 -f compose.sqlite.yaml down
docker compose -p hw6 -f compose.sqlite.yaml up -d --wait
curl -fsS http://127.0.0.1:8080/
```

Не запускать этот пример на том же порту одновременно с основной конфигурацией.

## Сдача

1. Выполнить `./scripts/run-all.sh` и проверить три файла логов.
2. Обновить `REPORT.md`, указав фактический результат и дату.
3. Создать свой репозиторий GitHub, добавить файлы проекта и логи.
4. Если репозиторий приватный — выдать доступ преподавателям.
5. Отправить ссылку в форму из `ASSIGNMENT.md`.

В репозитории также есть GitHub Actions: при push запускаются эти же проверки,
логи сохраняются как артефакт workflow `Docker homework checks`.
